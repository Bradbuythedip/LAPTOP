# Deploying from your own wallet

Everything in this directory is generated by `node test/run-deployable.mjs`, which compiles the
contracts, checks they are deployable at all, and runs every constructor with real encoded
arguments before writing anything. Regenerate rather than edit.

**Nothing here can deploy for you, and that is deliberate.** This repository holds no key, asks
for no key, and has no outbound network access. A key pasted into a build environment is a key
you have given away. Deployment happens from your wallet, in a tool you control.

## Is it deployable?

Yes, with room to spare. The limit that stops a deployment dead is EIP-170: a runtime over
24,576 bytes cannot be deployed at any gas price, and the transaction fails *after* the
constructor has run and been paid for.

| Contract | Init code | Runtime | Of the EIP-170 limit |
| --- | ---: | ---: | ---: |
| `SnoozeLaunchpad` | 13,021 | 12,993 | 52.9% |
| `Snooze` | 5,428 | 4,977 | 20.3% |
| `PooledLaunchBuy` | 4,462 | 3,828 | 15.6% |
| `LaunchTaxRamp` | 3,233 | 2,462 | 10.0% |

Compiled with solc 0.8.36, optimizer on, 200 runs. Change either and the bytes change, so
regenerate before you verify on a block explorer or the source will not match.

## What it costs

The other way a deployment fails after you have paid for it: a transaction needing more gas
than a block can hold never lands, at any price. `launch()` is the one to watch, because it
deploys two contracts and makes five state-changing calls inside a single transaction.

| Transaction | Execution gas | Of a 30M block |
| --- | ---: | ---: |
| Deploy `SnoozeLaunchpad` | 2,601,414 | 8.7% |
| `launch()` — token + pooled buy + wiring + freeze | 2,159,913 | 7.2% |
| Deploy `Snooze` alone (you do not need to) | 1,043,243 | 3.5% |
| Deploy `PooledLaunchBuy` alone (you do not need to) | 767,634 | 2.6% |
| Deploy `LaunchTaxRamp` | 633,844 | 2.1% |

**These are execution gas from an in-process EVM, not a quote.** They exclude the 21,000
intrinsic cost and the per-byte charge on your calldata, and they assume no other state. Read
them as "nothing here is near the ceiling", and let your wallet estimate the real number.

## Two runbooks, and this is the other one

**There are now two ways to launch in this repository and they do not agree, because they are
about different contracts.** This file describes the launchpad path: `SnoozeLaunchpad.launch()`
deploys `Snooze` and `PooledLaunchBuy` together and wires them, which needs a venue answering
`swapExactETHForTokens(address,uint256,address)` — and LAUNCH.md §2.2 records that nothing
deployed on Base is one.

`deploy/scripts/README.md` describes the **curve** path, where `SnoozeCurve` is its own venue,
`Snooze` is deployed from your own wallet, and `SnoozeDeployer` puts the curve on a chosen
address. The instruction below that you do *not* deploy `Snooze` yourself is about this file's
sequence and is still true of it; the other sequence deploys it deliberately, and says at length
why it cannot do otherwise.

Neither is wrong. Pick one before you send anything.

## The order, and why it is this order

You do **not** deploy `Snooze` and `PooledLaunchBuy` yourself. `SnoozeLaunchpad.launch()`
deploys both and wires them in one transaction, and that is the entire reason it exists —
`test/run-wiring.mjs` shows that hand-wiring them produces a distribution that cannot complete,
and you would find that out on distribution day with the money already in.

1. **Deploy the price oracle.** Not in this repo. It has to be a real pool observation on Base;
   the `MockOracle` in `contracts/test/` is settable and exists only so the suite can drive
   prices. Deploying the mock to mainnet would hand whoever holds it the ability to set the
   burn to anything.
2. **Deploy `SnoozeLaunchpad`.** No constructor arguments. This address is the launchpad
   forever; there is no upgrade path and no admin on it.
3. **Call `launch(params)`** from the wallet that will seed liquidity. One transaction. It
   deploys the token and the pooled buy, registers the venue, exempts the distributor, sends
   you the supply, and freezes the token. After it returns nobody can change a pool, an
   exemption or a rule — including you, including the launchpad.
4. **Seed the pool** with the supply you now hold, before anyone deposits.

`validate(params)` is `pure`. Call it first, for free, from anywhere. It returns the reason a
launch would be refused rather than making you find out by spending gas.

## The parameters

```
supply        uint256   base units, 18 decimals. Ultra-high supply is a units choice: price
                        is E/T, so it changes unit price and nobody's share.
oracle        address   step 1. Must be live and past 24h of history, or Rule 1 is off.
dev           address   receives devBps of the haircut. Ignored when devBps is 0.
devBps        uint256   share OF THE HAIRCUT, never of the trade. Capped at 2000 (20%).
                        Any value above 0 makes supplyOnlyFalls() return false.
router        address   the venue. Registered as a pool, and cap-exempt, inside launch().
executeAfter  uint64    unix seconds. No pooled buy before this.
refundAfter   uint64    unix seconds. Deposits refund unconditionally from here, and the
                        buy window CLOSES here. Must be at least a day after executeAfter.
minDeposit    uint256   wei. 0 is allowed.
exitFeeBps    uint256   charged on early exit only, and it stays in the pool for the
                        depositors who did not leave. It is never paid to you.
minTokensPerEth
              uint256   token base units per 1e18 wei. The worst price the pooled buy is
                        allowed to accept. Cannot be zero, and cannot be changed after
                        launch. See below — this is the parameter that decides whether a
                        stranger can take the pool.
```

### `minTokensPerEth` is not a formality

`execute()` is permissionless on purpose: anybody can push the button, so the buy does not
depend on you being awake. That also means the caller can be an attacker, and the caller
chooses `minOut`. Without a floor fixed at launch, the attack is three lines: move the price
on the venue, call `execute()` with `minOut = 1`, take the other side. The pool buys at
whatever price the attacker built, and every depositor holds the result.

`minTokensPerEth` is that floor, immutable and published before the first deposit. `execute()`
takes the stricter of it and the caller's `minOut`, so a caller can only ask for a *better*
price than you promised, never a worse one. Set it from the price you intend to seed at with
whatever slippage you are willing to eat — too tight and honest execution reverts, too loose
and you have re-opened the hole by degrees. `test/run-pooled.mjs` runs the attack against the
floor as a regression test.


## Before you send the launch transaction

- **Read `validate()` first.** It is free and it tells you which parameter is wrong.
- **The oracle is the one address you cannot get back.** It is immutable on the token. A
  settable oracle is a switch that sets the burn to anything, held by whoever holds it.
- **The router address must be right before you call.** `launch()` registers it and then
  freezes. A venue created afterwards is permanently outside both rules, and there is no call
  that adds one.
- **`minTokensPerEth` is the difference between a pooled buy and a donation.** It is
  immutable, so getting it wrong means relaunching. Zero is refused outright.
- **`devBps` is irreversible.** Above zero, the fixed-supply claim is false and the contract
  says so through `supplyOnlyFalls()`. Decide before, not after.
- **This has never been on a testnet.** It has been compiled and executed against an
  in-process EVM, which has no PoolManager, no real AMM, no mempool, no gas market and no
  reorgs. Deploy to Base Sepolia first and run a launch there.

## Verifying on a block explorer

Use solc 0.8.36 with the optimizer enabled at 200 runs, and the flattened source for the
contract you deployed. `manifest.json` lists the constructor inputs each one takes so you can
re-encode the arguments the explorer asks for. If the bytecode does not match, the compiler
settings differ — that is almost always the optimizer runs.

## What this does not cover

No audit. No testnet run. The economic findings in the root README under **`$SNOOZE`** are
unfixed and several are structural — most importantly that liquidity can migrate to a wrapper
or an unregistered venue that has neither rule, at which point the capped pool becomes a
reference price rather than the market.
